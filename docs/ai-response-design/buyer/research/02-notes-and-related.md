## 1. Buyer Note Structure

### Entity model

Buyer notes are stored as separate `NOTE` items in the same DynamoDB table as the parent buyer. They use the single-table design pattern.

| Field | Type | Required | Source / default |
|-------|------|----------|------------------|
| `PK` | `string` | Yes | `TENANT#<tenantId>#BUYER#<buyerId>` OR `TENANT#<tenantId>#CONTACT#<contactId>` if the buyer is a converted contact |
| `SK` | `string` | Yes | `NOTE#<uuidv4()>` |
| `EntityType` | `string` | Yes | `"NOTE"` |
| `tenantId` | `string` | Yes | copied from request |
| `buyerId` | `string` | Yes | the buyer ID passed to the function |
| `noteId` | `string` | Yes | UUID generated by `uuidv4()` |
| `content` | `string` | Yes | `data.content` (no default) |
| `createdBy` | `string` | No | `data.createdBy` or `"Admin"` |
| `createdAt` | `string` (ISO) | No | `data.createdAt` or `new Date().toISOString()` |

### Required fields for creation

- `tenantId` (function argument, throws if missing)
- `buyerId` (function argument, throws if buyer not found via `getBuyer`)
- `data.content` (stored as-is; no validation in the service)

### Optional fields

- `data.createdBy` (defaults to `"Admin"` for buyer notes; contrast with `"system"` for lead/owner/customer notes)
- `data.createdAt` (defaults to now)

### Internal keys to strip for AI DTOs

- `PK`
- `SK`
- `EntityType`
- `tenantId` (may be retained internally but should not be exposed to AI clients)

### Exposed keys to keep

- `noteId`
- `buyerId`
- `content`
- `createdBy`
- `createdAt`

## 2. How Buyer Notes Are Created and Retrieved

### Creation (`createBuyerNote`)

1. Validate `tenantId`.
2. Load the buyer via `getBuyer(tenantId, buyerId)`.
3. **Dual PK detection:** If the buyer is a converted/linked contact (`buyer.isFromContact && buyer.contactId`), the note is stored under the `CONTACT` partition key, not the `BUYER` partition key.
   - `pkId = buyer.contactId`
   - `pkPrefix = "CONTACT"`
   - Otherwise: `pkId = buyerId`, `pkPrefix = "BUYER"`
4. Generate a UUID `noteId`.
5. Write the note item with `PutCommand`.
6. Fire a contact activity log via `logContactActivity`:
   - `activityType: 'note_added'`
   - `subjectEntityType: 'buyer'`
   - `subjectEntityId: buyerId`
   - `title: 'Note Added (Buyer)'`
   - `description: data.content`
   - `performedBy: data.createdBy`
   - `payload: { noteId, content: data.content }`
7. The activity log is wrapped in a `try/catch`; note creation does not fail if logging fails.

### Retrieval (`getBuyerNotes`)

1. Validate `tenantId`.
2. Load the buyer via `getBuyer` (returns `[]` if buyer not found).
3. Resolve the same dual PK (`CONTACT` vs `BUYER`) as creation.
4. Query `PK = <resolved> AND SK begins_with "NOTE#"`.
5. Sort the result descending by `createdAt` (`newest first`).
6. Return the array.

### Relationship to buyers

- Notes are children of the buyer/contact partition.
- They are **not** embedded in the `BUYER` `PROFILE` item; they are separate items.
- The `buyerId` field is stored on the note for convenience, but the authoritative parent is the PK.

### AI DTO implications

- Buyer notes must be fetched as a separate list (not read from a `notes` scalar on the buyer).
- The buyer itself has a legacy `notes` scalar field (`buyer.notes`) which is a single string. The AI DTO should not confuse `buyer.notes` (scalar) with `buyerNotes` (list of NOTE entities).

## 3. Purchase Record Structure and Fields

### Location

Inside `createBuyer` (around line 4095):

```js
purchases: data.purchases || [],
// Each purchase: {
//   propertyId, purchaseDate, saleAmount, registrationDate, registrationNumber,
//   saleDeedS3Key, saleDeedUrl, registrationDocS3Key, registrationDocUrl,
//   stampDutyPaid, registrationCharges, brokeragePaid,
//   loanDetails: { bankName, loanAmount, loanAccountNumber, sanctionLetterS3Key },
//   notes
// }
```

### Purchase record fields

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `propertyId` | `string` | No | Reference to the purchased property |
| `purchaseDate` | `string` / `Date` | No | Date of purchase |
| `saleAmount` | `number` | No | Transaction amount |
| `registrationDate` | `string` / `Date` | No | Property registration date |
| `registrationNumber` | `string` | No | Government registration number |
| `saleDeedS3Key` | `string` | No | S3 key for the sale deed document |
| `saleDeedUrl` | `string` | No | Presigned/public URL for the sale deed |
| `registrationDocS3Key` | `string` | No | S3 key for the registration document |
| `registrationDocUrl` | `string` | No | URL for the registration document |
| `stampDutyPaid` | `number` | No | Stamp duty amount paid |
| `registrationCharges` | `number` | No | Registration charges paid |
| `brokeragePaid` | `number` | No | Brokerage/commission paid |
| `loanDetails` | `object` | No | Nested loan object |
| `loanDetails.bankName` | `string` | No | Lending bank name |
| `loanDetails.loanAmount` | `number` | No | Loan amount |
| `loanDetails.loanAccountNumber` | `string` | No | Loan account number |
| `loanDetails.sanctionLetterS3Key` | `string` | No | S3 key for the sanction letter |
| `notes` | `string` | No | Free-text notes about this purchase |

### Important facts

- Purchases are stored as an **array on the buyer profile item** (`purchases`), not as separate DynamoDB items.
- There is no explicit unique ID inside each purchase record in the comment; if the AI DTO needs to address individual purchases, it should probably derive a stable ID from `propertyId` + `purchaseDate`, or add a `purchaseId` in the schema.
- The array is initialized to `[]` if not provided.
- No CRUD helper functions exist in `crmDynamodbService.js` specifically for purchase records; they appear to be mutated directly via `updateBuyer` or via a generic buyer update.

### AI DTO recommendations

- Expose `purchases` as a list of normalized purchase objects.
- Consider adding a synthetic `purchaseId` (e.g., `propertyId` or a hash) to each purchase object for AI agent reference.
- Strip S3 keys (`saleDeedS3Key`, `registrationDocS3Key`, `sanctionLetterS3Key`) from the AI DTO and expose only the corresponding URLs, or provide both as `{ url, s3Key }` pairs.
- Normalize monetary fields (`saleAmount`, `stampDutyPaid`, `registrationCharges`, `brokeragePaid`, `loanDetails.loanAmount`) to numbers and provide a currency when known.
